# Как делался DetoxProxy

## Кто что делал

Работали три участника с жёстко разделёнными ролями.

| Роль | Кто | Что делал | Чего не делал |
|---|---|---|---|
| Заказчик и руководитель | участник команды | направлял работу: требования и приоритеты, выбор стека, решения по рискам и выкладке; исследования перед хакатоном и во время него (с помощью ChatGPT) и подготовка данных для оценки; тестировал демо и придумывал особые случаи для проверки (ФИО в смешанном регистре, PIN «от домофона», «цифры на обороте», знаменитости с инициалами); обеспечивал инфраструктуру — стенд, сеть, доступы; общение с организаторами | — |
| Архитектор и ревьюер | ассистент Claude (Anthropic) | архитектура и спецификация, ТЗ с исполняемой приёмкой, запуск агента через обвязку, ревью диффов и замечания агенту, коммиты, документация, презентация, инструменты проверки в `tools/` | не писал и не правил код продукта — ни модули, ни тесты, ни «мелкие правки» |
| Исполнитель | coding-агент DeepSeek-V4-Flash-0731 через AlfaGen (харнесс OpenCode, `opencode.json`) | весь код продукта: `src/`, `tests/`, `static/`, `Dockerfile` | не писал ТЗ и приёмку, не коммитил, не менял правила |

Разделение проверяемо: правила агента — `AGENTS.md`, правила архитектора — `CLAUDE.md` (в репозитории), каждый коммит с кодом помечен строкой `Generated-by: DeepSeek-V4-Flash-0731 (AlfaGen, OpenCode)` (больше 60 коммитов), ТЗ и приёмка — в `docs/agent-kit/`, исследования перед хакатоном — `docs/research/`, `docs/research-pii/`. Правило «архитектор не пишет код» введено заказчиком с первого дня, чтобы весь код продукта был работой агента AlfaGen.

## Цикл одной задачи

```
ТЗ (XML-разметка, исполняемая приёмка)
   → tools/agent.sh: агент в OpenCode, закрытый stdin, сторожок по времени и зависанию
   → независимая приёмка тем же скриптом (результат агента не принимается на слово)
   → ревью диффа: только разрешённые файлы, требования ТЗ в коде, нет ПД в логах
   → замечание агенту (REVIEW-N) или коммит
```

`tools/agent.sh` дополнительно сверяет контрольные суммы защищённых файлов (правила, приёмка, пороги качества) и HEAD до и после запуска: если агент поправил приёмку или сам сделал коммит, результат отбрасывается (`PROTECTED_FILE_CHANGED`, `AGENT_COMMITTED`).

## Якорная разметка

Постоянные правила агента — `AGENTS.md` (входит в архив), разбитый на XML-блоки: `<role>`, `<project>`, `<stack>`, `<api_verification>`, `<commands>`, `<layout>`, `<ownership_rules>`, `<pii_rules>`, `<streaming_rules>`, `<language>`, `<git>`, `<plan_first>`, `<rules>`, `<done_definition>`. Блоки позволяют модели не путать контекст, правила и задачу, а ТЗ — ссылаться на нужный блок.

Thinking у модели в AlfaGen выключен, поэтому блок `<plan_first>` требует сначала выписать файлы и шаги, а потом писать код: это заметно снизило число провалов на длинных задачах.

Каждое ТЗ — один блок `<task id="…">`: что сломано (таблица «вход / сейчас / нужно»), нумерованные правила, иногда готовый фрагмент кода, список разрешённых файлов и команда приёмки. Пример (сокращён):

```xml
<task id="T49">
Требование задания — текст до 100 000 токенов (~400 тыс. символов) в одном запросе.
Сейчас такой текст с адресами не укладывается в 5 с и получает 503. ...
1. city_word_number_span — на каждое слово-город разбирает весь остаток текста ...
2. number_follows_street — линейный проход по всем компонентам; нужен двоичный поиск ...
Главное условие: вывод детектора не меняется ни на одном тексте.
Приёмка: bash logs/T49.accept.sh
Файлы: src/detect/mod.rs, tests/perf_guard.rs.
</task>
```

## Приёмка вместо доверия

У каждой задачи — свой исполняемый скрипт приёмки. Типичный набор:

- `cargo clippy -D warnings` и лимит когнитивной сложности (как у анализатора жюри);
- все тесты (release — для тестов на время);
- `tools/check_process.py` — контракт `/process` (55 проверок), `tools/check_modes.py` — все режимы маскирования;
- `tools/manual_accept.sh` — 25 ручных кейсов с ловушками;
- `tools/eval_accept.sh` — размеченные наборы с порогами по типам (`tests/eval_floors.txt`): пороги только поднимаются;
- `tools/big_text_check.py` — текст на 100 000 токенов;
- локальный SonarQube — те же правила, что у автопроверки кода;
- для оптимизаций — `tools/compare_detect.py`: вывод нового детектора должен совпасть со старым на 15 727 текстах, включая отложенные наборы.

Отложенные наборы (`tests/data/holdout/`: HiveTrace, JayGuard, alrosait, scanpatch) только измеряются: ТЗ по их примерам не пишутся, иначе цифры качества перестают что-то значить.

## Статистика

По журналу запусков (`logs/runs.jsonl`, в архив не входит): 84 запуска агента по 55 задачам и раундам ревью: 48 прошли приёмку, 27 не прошли и ушли на новый раунд с замечанием, 9 остановлены обвязкой (изменён защищённый файл или коммит в рабочей ветке). Медианный запуск — 7 минут и 36 шагов, суммарно около 15 часов работы агента. Две дорожки шли параллельно в отдельных git worktree: детектор и данные — в одной, сервер, маскирование и демо — в другой.

## Чему научились

- Большое ТЗ из 3+ независимых частей агент без thinking не держит: такие задачи режутся заранее.
- Приёмка должна проверять, что задача действительно сделана, иначе на старом коде будет ложный «зелёный».
- Оптимизация принимается только при полностью совпадающем выводе: первая попытка ускорить детектор в 3,6 раза молча потеряла 4 п. п. полноты по ФИО.
- Пороги ловят только то, что в них записано: после каждой задачи сравниваются все типы, включая отложенные наборы.
- Незнакомый API крейта — сразу готовый фрагмент в ТЗ, иначе агент уходит читать исходники зависимостей.
