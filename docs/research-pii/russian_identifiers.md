# Российские идентификаторы: форматы и checksum

Дата доступа к источникам: 2026-09-22. Все примеры — синтетические.

## 1. ИНН (Идентификационный номер налогоплательщика)

Регулятор: ФНС России. Порядок: приказ ФНС от 29.06.2012 № ММВ-7-6/435@ (структура), алгоритм КС — открытая методика ФНС (публикуется на htmlweb.ru, pro-chislo.ru, docs Gosuslugi).

- Юрлицо: ровно 10 цифр. Структура: `XX` код субъекта РФ + `XX` код ИФНС + `XXXXX` номер записи + 1 КЦ.
- Физлицо/ИП: ровно 12 цифр. Структура: `XXXX` код НО + `XXXXXX` номер записи + 2 КЦ.

### ИНН-10

Веса для первых 9 цифр: `[2,4,10,3,5,9,4,6,8]`.

```
S = Σ d[i]*w[i], i=0..8
K = (S % 11) % 10
valid ⟺ K == d[9]
```

Пример valid: `7707083893` (Сбербанк, публично приводится в примерах brikkoAI/presidio-ru-recognizers и pro-chislo.ru):
`7*2+7*4+0*10+7*3+0*5+8*9+3*4+8*6+9*8 = 267; 267%11=3` → КЦ `3` ✓.
Пример invalid: `7707083892` (последняя цифра изменена).

Python (MIT-совместимый, собственная реализация):

```python
def validate_inn10(v: str) -> bool:
    if len(v)!=10 or not v.isdigit(): return False
    w=(2,4,10,3,5,9,4,6,8)
    return sum(int(d)*x for d,x in zip(v,w)) % 11 % 10 == int(v[9])
```

### ИНН-12

Веса1 (для d11): `[7,2,4,10,3,5,9,4,6,8]` по первым 10 цифрам.
Веса2 (для d12): `[3,7,2,4,10,3,5,9,4,6,8]` по первым 11 цифрам (включая d11).

```
K1 = (Σ d[0..9]*w1) % 11 % 10;  K1 == d[10]
K2 = (Σ d[0..10]*w2) % 11 % 10; K2 == d[11]
```

Пример valid: `500100732259` (пример с pro-chislo.ru / HF benchmark): K1=5, K2=9 ✓.
Пример invalid: `500100732258`.

Источники: htmlweb.ru/php/example/test_inn_bik_kpp_ogrn.php; helpbks.keysystems.ru/ro/info/keyinn; habr.com/ru/articles/1046397; pro-chislo.ru/validator/inn.

## 2. СНИЛС (11 цифр, ПФР/СФР)

Формат: `XXX-XXX-XXX YY`, где YY — контрольное число. Нормализация: удалить `[\s\-]`.

Алгоритм:
```
S = Σ d[i]*(9-i), i=0..8   # веса 9,8,7,6,5,4,3,2,1
если S < 100: K = S
если S == 100 или S == 101: K = 0  (записывается "00")
иначе: K = S % 101; если K == 100: K = 0
valid ⟺ K == int(d[9:11])
Особые случаи: номера ≤ 001-001-998 имеют K=00 (ранние выпуски).
```

Пример valid: `112-233-445 95` (S=95 → K=95 ✓, источник pro-chislo.ru/validator/snils).
Наивная ошибка: делать просто `S % 101` без ветки `100/101 → 00` — ломается на редких номерах (см. Habr 1046397).

Источники: info.gosuslugi.ru/articles/Валидация; habr.com/ru/articles/1046397; pro-chislo.ru/validator/snils.

## 3. ОГРН (13 цифр, юрлица) / ОГРНИП (15 цифр, ИП)

Регулятор: ФНС (приказ Минфина №165н — структура).

```
ОГРН:  K = int(v[0:12]) % 11 % 10; valid ⟺ K == int(v[12])
ОГРНИП: K = int(v[0:14]) % 13 % 10; valid ⟺ K == int(v[14])
```

Пример valid ОГРН: `1027700132195` (пример из README brikkoAI/presidio-ru-recognizers и Kontur.Focus).
Структура: `1` признак ОГРН + `02` год + `77` регион + `0013219` номер + `5` КЦ.
Пример invalid: `1027700132196`.

Источники: focus.kontur.ru/site/poisk/ogrn-po-inn; habr.com/ru/articles/1046397; htmlweb.ru (раздел ОГРН).

## 4. Банковская карта (Luhn)

- Длины: 13–19 цифр по ISO/IEC 7812, на практике 16 (Visa/Mastercard/МИР), 15 Amex (в РФ неактуален).
- Разделители в тексте: пробел, `-`, иногда `·`. Перед Luhn — strip `[\s\-]`.
- Luhn: с правого края удвоить каждую вторую цифру, вычесть 9 если >9, сумма %10==0.
- Защита от FP: требовать КС + длину + (опционально) BIN-префикс (2/4/5/МИР 2200–2204) + контекст («карта», «card», «номер карты»). Без Luhn любой 16-значный ID (таймстемп, PK) даст FP.
- Пример valid (тестовый, из Presidio docs): `4111 1111 1111 1111`. Пример invalid: `4111 1111 1111 1112`.

## 5. Банковский счёт (р/с, 20 цифр) + БИК/к/с

- Р/с: ровно 20 цифр. Полная КС зависит от БИК и к/с (алгоритм ЦБ: веса `7 1 3` циклически по строке `0 + 2 цифры БИК[5:7] + р/с` / к/с). Без справочника БИК ЦБ проверить нельзя — только формат.
- Поэтому в presidio-ru-recognizers `BANK_ACCOUNT_RF` — regex-only, низкий score, требует контекста (`р/с`, `расчётный счёт`, `счёт`).
- БИК: 9 цифр (`04...` — ЦБ). к/с: 20 цифр, тот же алгоритм ЦБ.
- Источник алгоритма ЦБ: htmlweb.ru (функция с весами `[7,1,3,...]`).

## 6. Только формат / только контекст (нет checksum)

| Сущность | Формат | Почему нет КС |
|---|---|---|
| Паспорт РФ | `\b\d{4}\s?\-?\d{6}\b` (серия 4 + номер 6) | КС не определена нормативкой. Только формат + контекст (`паспорт`, `серия`, `номер`, `выдан`) |
| Телефон РФ | `+7`/`8` + 10 цифр, разделители `[\s\-\(\)]*` | Формат строгий (11 цифр после нормализации), но КС нет. FP-риск: даты, ID |
| ВУ (водительское) | `99 99 999999` (10 цифр как паспорт) | КС нет. Только контекст (`права`, `в/у`, `водительское`) |
| Дата рождения/выдачи | `dd.mm.yyyy`, `dd месяца yyyy`, ISO | Только формат + контекст (`дата рождения`, `г.р.`, `выдан`) |
| Код подразделения | `XXX-XXX` | Формат + контекст (`код подразделения`) |
| CVV/CVC | `\b\d{3}\b` (Amex 4) | Слишком короткий — только контекст (`CVV`, `CVC`, `код безопасности`) |
| PIN | `\b\d{4}\b` | Только контекст (`PIN`, `пин-код`) |
| Email | RFC-5322 упрощённый | Формат достаточен, контекст не нужен |
| Адрес | свободный текст | Только ML/словари + контекст |

Вывод для архитектора: `имеет checksum` → ИНН-10/12, СНИЛС, ОГРН/ОГРНИП, карта (Luhn), счёт (ЦБ, требует БИК) — можно резать FP дешёвой арифметикой. Всё остальное — `формат+контекст` или `ML` (ФИО, адрес, место рождения, орган выдачи).
