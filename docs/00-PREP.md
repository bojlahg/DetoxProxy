## 2. Рекомендация по стеку

**Итоговое решение: Rust (axum + hyper + reqwest) с контрольной точкой, запасной вариант — Go на stdlib `net/http`.** Таблица ниже — исходная оценка до эксперимента; как решение менялось и чем подтверждено, см. «Решение по стеку» и «Проверка стека экспериментом».

| Вариант | Производительность | Риск с DeepSeek V4 Flash | Знакомство жюри | Итог |
|---|---|---|---|---|
| Go, `net/http` | p99 overhead единицы ms, 4–5k RPS на 2 vCPU, ~30 KB на стрим | низкий: сборка за секунды, отмена upstream через `r.Context()` | Go в Альфе используется | **брать** |
| Rust, axum + hyper + reqwest | лучший p99 (<1 ms), память в 3–10 раз меньше | высокий: `Send + 'static`, типы Body, дрейф API крейтов, долгая сборка | Rust в Альфе не встречается | только если оценка идёт чисто по замерам overhead |
| Rust, Pingora | максимум для proxy | очень высокий: API плохо известен моделям, нет сборки под Windows | — | нет |
| C++ (Drogon, Boost.Beast, userver) | верхняя лига наравне с Rust, без GC | очень высокий: нет единого стека (HTTP/2, TLS, пул, Redis, метрики собираются по частям), сборка минутами, use-after-free в асинхронном коде роняет весь процесс под нагрузкой | C++ в Альфе не встречается | только если в команде сильный C++-разработчик; иначе при той же скорости безопаснее Rust |
| C с нуля (libuv, llhttp, nghttp2, libcurl) | максимум, уровень nginx и HAProxy | запредельный: нет корутин и RAII, ручные буферы на каждом SSE-чанке, любая ошибка — segfault или переполнение буфера в прокси с PII | — | нет |
| OpenResty (nginx + LuaJIT), путь Kong | высокая: у Kong 29k RPS, p99 30 ms | высокий: в `body_filter` нет сетевых вызовов, hedging и fallback поверх `proxy_pass` почти не делаются, модель плохо знает фазы OpenResty | — | нет; nginx или HAProxy использовать как L7-балансировщик перед Go-репликами |
| Go, fasthttp | выигрыш только в микробенчмарках | нет HTTP/2, отключение клиента ловится костылями | — | нет |
| Kotlin/Java, Spring WebFlux или Vert.x | приемлемо с ZGC, память выше | средний | основной стек Альфы | запасной, если стек навязан |
| .NET, Kestrel + YARP | высокая | средний | — | запасной |
| Python, Node | отстают на порядки под нагрузкой | низкий | — | только если навязаны |

Исходный довод против Rust (снят экспериментом 21.09: агент справился с Rust за 3 минуты и дал более корректный код, чем на Go): разница в overhead между Go и Rust — 1–4 ms при TTFT модели от 100 ms до секунд, то есть доли процента от SLA. Качество реализации важнее языка: в независимом бенчмарке ENTERPILOT Go-шлюз обошёл Rust-шлюз из-за невыставленного `TCP_NODELAY`. А риск не успеть фичи с Rust и слабой моделью заметно выше.

### Решение по стеку (обновлено после обсуждения)

Вводные изменились: код пишет DeepSeek V4 Flash-0731, но архитектуру, сигнатуры типов, тесты приёмки и ревью диффов делает сильная модель (Claude или Codex). Это снимает главный риск Rust — агент, застрявший в типах и владении. Дополнительно Rust отличает решение от массы Go-прокси и даёт сильные цифры для презентации (p99 < 1 ms, десятки MB памяти, нет GC), а компилятор работает как второй ревьюер ИИ-кода: гонки данных и use-after-free не проходят сборку.

**План: Rust (axum + hyper + reqwest) с контрольной точкой. Подтверждено пользователем 21.09: если стек можно выбирать — Rust.**

- **Контрольная точка — 2 часа от старта.** Должно быть: сквозной SSE-прокси, отмена upstream при отключении клиента, `/metrics`, зелёный интеграционный тест с mock. Если нет — без обсуждений переходим на Go; SPEC и TASKS от языка не зависят.
- **Вторая точка — 12 часов.** Если блок 2 (breaker, балансировка, rate limit, очередь, hot reload) готов меньше чем наполовину — оценить переход на Go или урезание блока 3. Прокси с половиной функций проигрывает прокси со всеми, на каком бы языке он ни был.
- Mock-upstream и генератор нагрузки — на Go в любом случае.
- Разделение ролей: сильная модель задаёт каркас (модули, публичные типы и сигнатуры, владение, точные API крейтов, тесты), Flash заполняет тела функций под `cargo check`. Правила для агента — `docs/agent-kit/AGENTS.rust.md`.
- Окружение: `rustup` + MSVC Build Tools либо разработка в WSL; release-сборка в Docker под Linux; аллокатор mimalloc.
- На брифинге уточнить, разрешено ли использовать другие ИИ для планирования и ревью.

### Проверка стека экспериментом (21.09, вечер)

Одно ТЗ на мини-прокси выдано DeepSeek-V4-Flash-0731 через OpenCode на трёх стеках, приёмка — общая чёрный ящик-проверка из 10 тестов. Все три дошли до 10/10 без вмешательства. Подробности и ревью кода — `bakeoff/RESULTS.md`.

| | Go | Rust | C |
|---|---|---|---|
| Время агента | 1,5 мин | 3 мин | 12,4 мин |
| Выходных токенов | 8 тыс. | 11 тыс. | 53 тыс. |
| Строк кода | 211 | 181 | 827 |
| Серьёзные ошибки, не пойманные приёмкой | гонка с `ResponseWriter`, нет пула соединений | нет | блокирующий DNS в event loop, одно ядро |

Итог: C отпадает по цене (в 4–8 раз дольше Rust на задаче без TLS и HTTP/2). Rust реален и дал более корректный код, чем Go. Решение «Rust с контрольной точкой, запасной Go» подтверждено.

Находки про AlfaGen, сделанные по ходу:
- Endpoint принимает только `stream: true`; запрос без стриминга получает `400` с пустым телом.
- Формат SSE на двух путях разный: `data:{` без пробела на `/chat/completions` и `data: {` на `/v1/chat/completions`. Парсер прокси обязан принимать оба.
- Шлюз сам добавляет системный промпт и, судя по одинаковым `id` ответов, кеширует одинаковые запросы.
- В `opencode.jsonc` обязателен блок `limit` (`context: 1000000`, `output: 30000`) — в исходной настройке его не было.
- **Thinking на AlfaGen выключен и клиентом не включается.** Проверено тремя способами: прямые запросы с десятью вариантами параметров (`thinking`, `reasoning_effort`, `reasoning`, `chat_template_kwargs`, `enable_thinking` и др.) на обоих путях; OpenCode с `reasoning: true`; перехват реальных запросов Kilo Code. Во всех ответах `reasoning_content` пустой. Поведенческий тест: умножение 6-значных чисел «только числом» — 0 из 5 верно за 0,4 s; с требованием расписать по шагам — 3 из 5. Галочка «Рассуждение» в Kilo на основные запросы не влияет (добавляет `reasoning_effort: low` только в запрос генерации заголовка чата).
- **Ловушка Kilo Code:** после добавления провайдера alfagen чат по умолчанию продолжает использовать `kilo / kilo-auto/free` — бесплатную облачную модель Kilo. Модель нужно явно выбрать в переключателе под полем ввода. Проверка — в логе `~/.local/share/kilo/log/`, строки `message=stream providerID=...`.
- Следствия: спросить поддержку, можно ли включить thinking на стороне сервера; в правила агента добавить обязательный видимый план перед кодом (замена рассуждению); сессии держать короткими; планирование и ревью — на сильной модели.

### Как закрывать «гибкость»

Два прочтения требования: архитектурное (система дёшево переживает изменения) и буквальное (организаторы могут поменять требования посреди хакатона). Принцип для обоих: изменчивое живёт в конфиге, а не в коде — для Rust это важно вдвойне, рефакторинг типов агентом дороже, чем в Go.

| Изменение | Механизм | Рестарт |
|---|---|---|
| Добавить или убрать провайдера, upstream | `providers` в конфиге + Admin API | нет |
| Провайдер с другим форматом API | внутренняя модель событий + адаптер (модуль + ветка `enum Provider`; exhaustive `match` покажет все места для доработки) | да |
| Сменить модель, не трогая клиентов | виртуальные алиасы моделей | нет |
| Веса, canary, порядок fallback | декларативные `routes`, версия, откат | нет |
| Таймауты, retry, breaker, лимиты тенанта | конфиг с переопределением на уровне маршрута | нет |
| Новый шаг обработки потока | конвейер стадий (`on_request`, `on_chunk`, `on_end`), состав и порядок — в конфиге на маршрут | нет, если стадия написана |
| Новый endpoint (`/v1/embeddings`, `/v1/responses`) | прозрачный режим: любой `/v1/*` проксируется с той же маршрутизацией, лимитами и отказоустойчивостью | нет |
| Особенности upstream | флаги у провайдера (`force_stream` и др.), терпимый SSE-парсер | нет |
| Redis недоступен или заменён | состояние за трейтом: память или Redis | нет |

Примеры из практики с AlfaGen: endpoint принимает только `stream: true` — флаг `force_stream` превращает обычный запрос клиента в стрим и собирает ответ обратно в JSON; формат SSE на двух путях разный (`data:{` и `data: {`) — парсер принимает оба.

Демо гибкости (под нагрузкой, без рестарта, 0 оборванных стримов): добавить провайдера через Admin API → переключить алиас → canary 10% → 50% → включить PII для одного тенанта → невалидный конфиг отклонён → откат. В README — таблица «изменение → что правим → рестарт → минуты».

Гибкость процесса: спека → задачи с исполняемой приёмкой → чёрный ящик-проверка. Если требования поменяют на ходу — засечь время от объявления до зелёной проверки и показать на защите.

### Как доказывать «кратный рост нагрузки»

Постоянный множитель от стека (условные 1,6× у nginx против Pingora в одном hello-world-замере) — это не масштабируемость, а цена одной дополнительной реплики. Разрыв в том замере объясняется архитектурой nginx (процесс на ядро, минимум аллокаций), а не языком; то же достижимо в Rust.

- **Ориентир масштаба:** на апрельском хакатоне AlfaGen обработал 96 тыс. запросов за сутки (~1 RPS в среднем) с пиком 20 тыс. токенов в секунду. Одна реплика прокси с 10k стримов по 50 токенов в секунду — это 500 тыс. токенов в секунду, в 25 раз больше. Узкое место системы — GPU, а не прокси.
- **Что мерить и показывать:** график «число реплик → пропускная способность» (1, 2, 4 реплики, рост близок к линейному); число одновременных стримов и память на стрим; p99 overhead при росте нагрузки ×1 / ×3 / ×10; нагрузка на Redis на один запрос (локальная аренда квоты делает её почти нулевой); автоскейлинг по in-flight стримам; поведение при перегрузке upstream (очередь, shedding, деградация).
- **Запас от стека без смены языка:** отдельный tokio-рантайм на ядро + `SO_REUSEPORT`, mimalloc, склейка мелких чанков в одну запись под нагрузкой (окно 5–10 ms), пересылка сырых байт без разбора JSON, общий прогретый пул соединений к upstream.
- В README — раздел «Рост ×10 и ×100»: что масштабируется добавлением реплик, что упрётся первым (Redis → кластер или шардирование по tenant; порты и соединения к upstream → HTTP/2; генератор нагрузки) и что с этим делать.

**Если стек навязан платформой:**

- **JVM:** JDK 21+ и virtual threads либо Spring WebFlux + Reactor Netty `WebClient` (жюри знает), ZGC, `Flux<ServerSentEvent>` без буферизации. Максимум скорости — Vert.x / чистый Netty.
- **Python:** Starlette/FastAPI + `httpx.AsyncClient` (общий пул, HTTP/2) или aiohttp, uvloop, сервер granian или uvicorn с несколькими воркерами, orjson. Масштабировать процессами, состояние — в Redis.
- **Node/TS:** Fastify или чистый `http` + undici (pool, `pipeline`), cluster по числу ядер, без Express.
- **.NET:** YARP + Kestrel, `IHttpForwarder`, transforms для потока.

Архитектура и паттерны ниже от языка не зависят.

## 3. Целевая архитектура

```
Client (OpenAI-compatible API, SSE)
  → L4/L7 LB (least-connections)
  → Proxy, stateless, N реплик
       auth → admission/priority → rate-limit (local + Redis) → cache (exact, singleflight)
       → input guardrails (PII mask) → router (alias → pool → endpoint; breaker, P2C peak-EWMA)
       → upstream adapter (OpenAI-compatible / Anthropic / GigaChat / YandexGPT / vLLM)
       → stream pipeline (SSE parse → normalize → guardrail/rehydrate → token count → re-emit + flush)
       → async sink (usage, cost, audit)
  ↔ Redis (лимиты, кеш L2, config pub/sub)
  ↔ Prometheus + Grafana, OTel
```

Как это отвечает на формулировку задачи:

| Требование | Чем закрываем |
|---|---|
| SLA по времени отклика | раздельные таймауты connect / TTFT / idle / total, deadline propagation, hedged requests, P2C + peak-EWMA по TTFT, метрика `proxy_overhead_seconds` |
| Отказоустойчивость | retry с full jitter и retry budget (только до первого байта клиенту), fallback-цепочка, circuit breaker на upstream, outlier detection, graceful degradation, работа без Redis |
| Масштабируемость, кратный рост | stateless-реплики, adaptive concurrency, очередь с приоритетами и load shedding, локальная аренда квоты вместо Redis на каждый запрос, HPA/KEDA по in-flight стримам, drain длинных стримов |
| Гибкость | внутренняя каноническая модель + адаптеры провайдеров, virtual model aliases, декларативные routes, hot reload (atomic snapshot, версия, rollback), canary-веса, feature flags, middleware-pipeline |
| «На лету, без шаблонов, с погружением в контекст» | потоковый конвейер над событиями, а не буферизация ответа; потоковая трансляция форматов; PII mask → LLM → rehydrate с hold-back на границах чанков; policy-routing по содержимому (есть PII → только on-prem модель); подсчёт токенов на лету |

### Обязательные технические мелочи (на них обычно теряют p99)

- `Flush()` после каждого SSE-события; `X-Accel-Buffering: no`; без gzip на SSE; `DisableCompression: true` на upstream-клиенте.
- `TCP_NODELAY` включён (в Go по умолчанию; в axum — явно).
- `MaxIdleConnsPerHost` поднять с 2 до сотен; прогрев соединений при старте; HTTP/2 к внешним провайдерам.
- `Server.WriteTimeout = 0`, дедлайн на каждый чанк через `http.ResponseController`.
- Отключение клиента отменяет upstream-запрос (`NewRequestWithContext(r.Context())`).
- Не читать SSE через `bufio.Scanner` с дефолтным буфером 64 KB.
- Из тела запроса доставать только `model` и `stream` (gjson), без полного разбора; в запрос добавлять `stream_options.include_usage`.
- Ошибка после ответа 200 — in-band событие `data: {"error":...}`; heartbeat-комментарий каждые 15 s.
- Async-логирование через ограниченный буфер: при переполнении запись отбрасывается, запрос не блокируется.

Дефолты параметров (таймауты, retry, breaker, очередь, лимиты, кеш, shutdown) — в разделе 11 файла `docs/research/02-architecture-playbook.md`.

### Сценарий демо (5–7 минут, Grafana открыта, k6 даёт постоянную нагрузку)

1. Базовая линия: overhead p99 напрямую против через прокси.
2. Убить провайдера A → breaker открывается, fallback на B, ошибок у клиента нет.
3. Замедлить провайдера (toxiproxy) → hedging и EWMA уводят трафик, p99 TTFT в SLO.
4. Нагрузка ×3–×5 → sheddable получает 429, critical держит SLO, добавляются реплики.
5. Hot reload: вес canary 10% → 50%, смена алиаса модели без рестарта и обрыва стримов, rollback.
6. PII: запрос с картой, ИНН, ФИО → в логе mock видны плейсхолдеры, клиент получает восстановленный ответ.
7. 100 одинаковых одновременных запросов → один вызов upstream.
8. Rolling restart под нагрузкой → ни одного оборванного стрима.

## 5. Работа с DeepSeek V4 Flash

- Развёрнута версия 0731. Её агентное качество примерно вдвое выше 0423-preview (среднее по агентным бенчмаркам 55.2 против 29.6, цифры из вторичного источника), на коротких агентных задачах она обходит даже Pro-preview.
- Лимит вывода 30 000 токенов: не просить агента создавать много больших файлов за один ход, файлы держать до 300–400 строк.
- Харнесс: KiloCode (рекомендован организаторами). В стороннем сравнении на V4 Flash KiloCode дал 49.5% против 47.6% у OpenCode — разница в пределах погрешности, выбирать по удобству. В Kilo планирование вести в режиме Architect, исполнение — в Code, по одной задаче из TASKS.md на сессию.
- **Thinking включать, effort не ниже high.** В non-think модель резко проседает на длинном контексте.
- «Flash executes. It doesn't plan»: план и декомпозицию делает человек. Flash получает задачи на 1–3 файла с явным критерием приёмки.
- Слабости: деградация tool calling при большом контексте и большом числе инструментов; выдуманные API библиотек; правка несвязанных файлов; зацикливание на падающем тесте; многословность.
- Противодействие: короткие сессии, минимум MCP и инструментов, stdlib в приоритете, закреплённые версии, правило «перед использованием API смотри `go doc`», коммит после каждого зелёного шага, лимит 2–3 попытки ремонта, затем сброс контекста.
- Если агент «теряет» вызовы инструментов на self-hosted модели — это известная проблема DSML-парсера vLLM/SGLang (теги утекают в content), лечится на стороне платформы; сообщить организаторам.
