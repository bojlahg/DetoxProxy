# SPEC v2 — Модуль безопасности персональных данных (PII-прокси для LLM)

Основание: `docs/brief/BRIEF.md` (ТЗ трека, контракт `/process`, критерии). Стек: Rust (axum + tokio), один статический бинарник `pii-guard`. Язык текстов — русский (английский — плюс).

## 1. Что делает модуль

Стоит между системой-потребителем и LLM. Три операции над текстом:
1. **Идентификация** — найти спаны персональных данных (ПДн) и определить их тип.
2. **Маскирование** — заменить спаны по правилу потребителя, запомнить соответствие.
3. **Демаскирование** — по тексту с масками восстановить исходные значения (в том числе в ответе LLM, где токены переставлены и окружены другим текстом).

Ключевая идея: маска по умолчанию — **токен `<<LABEL_N>>`** (`<<FIO_1>>`, `<<CARD_1>>`), стабильный в пределах одного запроса (одинаковое значение → один и тот же токен; нумерация с 1 в каждом запросе). Формат выбран так, чтобы не совпадать с кодом, JSON, markdown и HTML и чтобы LLM возвращала его дословно; настраивается в реестре (`token_format`). LLM переносит токен в ответ дословно, модуль подставляет исходное значение обратно. Так сохраняется смысл запроса и работает демаскирование ответа.

## 2. Внешний API

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/process` | **контракт автопрогона** (Приложение A): `{payload, payload_id}` → `{result}`. Первый запрос с новым `payload_id` — маскирование; второй с тем же — демаскирование. Идемпотентен: повтор того же запроса даёт тот же ответ. |
| POST | `/v1/mask` | `{text, system_id}` → `{text, session_id, entities:[{type, start, end, token}]}` — маскирование с явным контекстом |
| POST | `/v1/unmask` | `{text, session_id}` → `{text}` — демаскирование любого текста (в т.ч. ответа LLM) по сессии |
| POST | `/v1/detect` | `{text, system_id}` → `{entities:[...]}` — только идентификация, без изменения текста |
| POST | `/v1/chat/completions` | OpenAI-совместимый прокси: маскирует `messages`, шлёт в upstream LLM, демаскирует ответ (stream и non-stream) |
| GET | `/healthz`, `/readyz` | liveness / readiness |
| GET | `/metrics` | Prometheus |
| GET | `/admin/config` | текущая конфигурация (без секретов) |
| PUT | `/admin/config` | атомарная замена конфигурации с валидацией; hot reload также по изменению файла |

Аутентификация потребителей: заголовок `X-System-Id` (для `/process` — потребитель по умолчанию из конфига `default_system`). Система вне списка или выключенная → 403. Ошибки — JSON `{"error": {"message", "type"}}`.

Перегрузка: при превышении лимита одновременных запросов — **429 + `Retry-After: 1`**, никогда не 5xx от перегрузки.

## 3. Хранилище соответствий и жизненный цикл токенов

Только память процесса (`DashMap`), TTL, никакого диска и БД: исходные значения не покидают процесс, забывание — часть «минимизации данных». Два режима, на потребителя:

| Режим | Ключ | Что хранится | Живёт |
|---|---|---|---|
| `stateless` (по умолчанию; `/process`, LLM-прокси с открытой историей от клиента) | `payload_id` / `request_id` | карта одного запроса | до демаскирования ответа, TTL 15 мин (ретраи с тем же id получают тот же ответ) |
| `stateful` (клиент хранит уже замаскированную историю) | `session_id` | карта сессии, дополняется новыми сущностями | скользящий TTL 60 мин, продлевается при обращении |

Нумерация токенов (`token_numbering`, на потребителя):
- `sequential` (по умолчанию) — `<<FIO_1>>`, `<<FIO_2>>` по порядку первого появления. Детерминирована, поэтому append-only история диалога маскируется одинаково и prompt-кеш провайдера не сбрасывается.
- `hash` — `<<FIO_a3f9c1>>`: 6 hex из HMAC-SHA256(соль потребителя из конфига, нормализованное значение). Один человек → один токен в любом запросе и порядке, кеш стабилен даже при перестановках истории. Соль на потребителя исключает связывание запросов между системами. Обратимость та же — через карту.

`/admin` никогда не отдаёт содержимое хранилища, только счётчик записей. Для нескольких реплик — sticky по id на балансировщике либо Redis с шифрованием значений ключом потребителя (описать в README, не реализовывать).

## 4. Типы ПДн (реестр, обязательное покрытие — 17 типов ТЗ)

| id | Тип | Метод детекции | Валидация |
|---|---|---|---|
| `fio` | ФИО | словари фамилий/имён/отчеств + морфология окончаний + шаблон «Фамилия Имя Отчество / И. О. Фамилия» + контекст («клиент», «гражданин», «ФИО:») | ≥2 компонента или 1 компонент + контекстное слово |
| `birth_date` | Дата рождения | дата (любой формат) + контекст («родился», «дата рождения», «д.р.», «г.р.») | валидная календарная дата |
| `birth_place` | Место рождения | контекст («место рождения», «родился в», «уроженец») + топоним | — |
| `passport` | Серия и номер паспорта РФ | `NNNN NNNNNN` с разделителями и словами «серия/номер», «паспорт» | 4+6 цифр |
| `citizenship` | Гражданство | контекст («гражданство», «гражданин») + словарь стран/прилагательных | словарь |
| `passport_issuer` | Орган, выдавший паспорт | контекст («выдан», «кем выдан») + шаблон до даты/кода подразделения | — |
| `subdivision_code` | Код подразделения | `NNN-NNN` + контекст («код подразделения») | 3+3 цифры |
| `passport_issue_date` | Дата выдачи паспорта | дата + контекст («дата выдачи», «выдан … г.») | валидная дата |
| `driver_license` | Серия и номер ВУ | `NN NN NNNNNN` / `NNAA NNNNNN` + контекст («в/у», «водительское») | 10 знаков |
| `address` | Адрес (и компоненты: страна, индекс, город, улица, дом, квартира) | грамматика адреса: индекс 6 цифр, «г./город», «ул./улица/пр-т/пер.», «д./дом», «кв./квартира», словарь городов | ≥2 компонента |
| `email` | Email | RFC-упрощённый шаблон | — |
| `phone` | Телефон | `+7/8 (XXX) XXX-XX-XX` и вариации, 10–11 цифр | код региона |
| `inn` | ИНН | 10 или 12 цифр | контрольные разряды |
| `card_number` | Номер карты | 13–19 цифр с пробелами/дефисами | Luhn |
| `cvv` | CVV | 3–4 цифры + контекст («cvv», «cvc», «код безопасности») | — |
| `card_pin` | ПИН-код карты | 4 цифры + контекст («пин», «pin») | — |
| `card_holder` | Имя держателя карты | латиница `NAME SURNAME` + контекст («держатель», «cardholder») или рядом с номером карты | — |
| `snils` | СНИЛС (расширение, не в ТЗ) | `NNN-NNN-NNN NN` | контрольная сумма |

Реестр — **данные, не код**: каждый тип описан в YAML (`patterns`, `context_words`, `validator: luhn|inn|date|none`, `dictionary: fio_surnames`, `min_confidence`, `mask`). Новый тип без валидатора добавляется правкой YAML. Валидаторы — фиксированный набор функций, выбираемых по имени.

Регистр не учитывается. Даты: `дд.мм.гггг`, `дд/мм/гггг`, `гггг-мм-дд`, `мм.дд.гггг`, `д месяц гггг` текстом («5 мая 1985», «пятого мая»), с «г.»/«года».

### Метки токенов (token_label в реестре)
| Тип | Метка | Тип | Метка |
|---|---|---|---|
| ФИО | `FIO` | Адрес | `ADDR` |
| Дата рождения | `BDATE` | Email | `EMAIL` |
| Место рождения | `BPLACE` | Телефон | `PHONE` |
| Паспорт | `PASSPORT` | ИНН | `INN` |
| Гражданство | `CITIZEN` | Карта | `CARD` |
| Орган выдачи | `PASSISS` | CVV | `CVV` |
| Код подразделения | `SUBDIV` | ПИН | `PIN` |

В системный промпт LLM-прокси добавляется строка: «Placeholders like <<FIO_1>> denote masked personal data; keep them exactly as they are.»

## 5. Принадлежность к ПДн (ловушки жюри)

- **Allow-list**: публичные персоны (словарь: Пушкин, Толстой, президенты и т.д., расширяемый), адреса организаций/отделений банка (конфиг потребителя), служебные телефоны (8-800, короткие).
- **Контекстные признаки «не ПДн»**: «поэт», «писатель», «композитор», «отделение банка», «офис», «филиал», «горячая линия», «пример», «тестовый».
- **Правило комбинаций** (настраиваемое, по умолчанию выключено): типы с `requires_companion: true` (cvv, card_pin) маскируются только при наличии в тексте другого однозначного типа (card_number). ТЗ: «пин-код» — не маскируем, «пин-код + номер карты» — маскируем.
- **Уверенность**: каждый детектор возвращает `confidence` 0..1 (валидатор прошёл — высокая, только шаблон — средняя, только контекст — низкая); порог на тип и на потребителя. По умолчанию порог низкий: утечка дороже ложного срабатывания.

## 6. Маскирование

Режим — на потребителя и на тип (тип переопределяет потребителя):

| Режим | Результат | Обратимость |
|---|---|---|
| `token` (по умолчанию) | `<<FIO_1>>`, `<<CARD_2>>` — один токен на уникальное значение в запросе | полная, в любом порядке и окружении |
| `stars` | сохраняет длину и структуру: `И. И. И.` для ФИО (инициалы), `45** ****56` для документов (открыты первые/последние N по типу), `+7 (9**) ***-**-89` для телефона, `i***@mail.ru` для email | по карте сессии |
| `synthetic` | правдоподобная замена того же типа (другое ФИО из словаря, валидная по Luhn карта) | по карте сессии |
| `remove` | `[удалено]` | по карте сессии |
| `off` | тип не маскируется для этого потребителя | — |

Замены применяются справа налево по позициям, чтобы смещения не сбивались; пересекающиеся спаны разрешаются в пользу более длинного/уверенного. Результат маскирования детерминирован для одного `payload_id`.

Документация масок по каждому типу — обязательный файл `docs/MASKS.md` (требование организаторов: «приложить, какие маски используете»).

## 7. Демаскирование

- По `session_id`/`payload_id` из хранилища. Токены ищутся регуляркой `<<\s*([A-Za-z_]+)_(\d+)\s*>>` без учёта регистра и с допуском пробелов внутри скобок (LLM может исказить); каждый заменяется исходным значением. Для `stars`/`synthetic` — поиск маски как подстроки.
- Работает на любом тексте: ответ LLM может содержать токены в другом порядке, часть токенов, токены внутри SQL/JSON/кавычек.
- «С сохранением местоположения знаков»: позиции и окружение сохраняются, заменяется только сам спан.
- Round-trip инвариант: `unmask(mask(x)) == x` побайтово для любого x из датасета — обязательный тест.

## 8. Конфигурация (YAML, hot reload)

```yaml
version: 1
server: { listen: "0.0.0.0:8080", max_body_bytes: 4194304, max_inflight: 2048, mapping_ttl_sec: 900, mapping_max_entries: 200000 }
default_system: autotest              # используется для /process без X-System-Id
systems:
  - id: autotest
    enabled: true
    mask_mode: token                   # token | stars | synthetic | remove
    unmask_enabled: true
    types: all                         # или список id типов
    overrides: { cvv: stars }          # режим на тип
    combination_rule: false            # requires_companion в силе?
    min_confidence: 0.3
    allow_addresses: ["ул. Каланчёвская, д. 27"]   # адреса организаций — не ПДн
  - id: chatbot
    enabled: true
    mask_mode: token
    unmask_enabled: false              # ответ LLM клиенту уходит с токенами
    types: [fio, phone, email, card_number, passport]
upstream: { base_url: "https://alfagen.alfabank.ru/continue-dev", api_key_env: "LLM_API_KEY", timeout_ms: 60000, force_stream: true }
pii_types: !include pii_types.yaml     # реестр типов (или inline)
allowlist: !include allowlist.yaml     # публичные персоны, организации
```

Замена конфига атомарна (`ArcSwap`); невалидный конфиг отклоняется, старый остаётся. Инструкция по настройке в README — не более 5 предложений (требование ТЗ).

## 9. Логи и метрики

- Лог на запрос (JSON, stdout): `request_id`, `system_id`, `direction` (mask/unmask), `payload_id`, `entities: [{type, start, end, confidence}]` — **значений нет никогда**, ни в логах, ни в метриках, ни в ошибках. Отдельный тест: лог за прогон датасета не содержит ни одного исходного значения.
- Метрики: `pii_requests_total{system,direction,status}`, `pii_latency_seconds{direction}` (гистограмма), `pii_entities_total{type}`, `pii_inflight`, `pii_tokens_per_second` (символы/4 как оценка), `pii_mappings_stored`, `pii_rejected_total{reason}`.
- Ошибки API: 400 (невалидный JSON/отсутствует поле), 403 (система не разрешена), 404 (session/payload_id неизвестен при демаскировании — вернуть текст как есть с `X-Unmask: not-found`, 200), 413, 429 + `Retry-After`, 502 (upstream LLM), 503 (readiness).

## 10. Производительность

- Цель: 1000 RPS при p99 < 100 мс на текстах датасета (короткие предложения), 2000 RPS — плюс. Таймаут проверяющей — 10 с; наш внутренний дедлайн на запрос — 5 с.
- Детекция линейная по тексту: один проход токенизации + набор компилированных регулярок (`regex` crate, `RegexSet` для предварительной фильтрации) + словарные проверки через `HashSet`/FST. Без внешних сервисов, без Python.
- До 100 000 токенов (~400 KB текста): потоковая обработка по абзацам, лимит тела 4 MB.
- Ограничение одновременных запросов семафором → 429.

## 11. Качество

- Свой размеченный датасет `tests/data/pii_dataset.jsonl`: ≥300 примеров, все 17 типов, по 3+ варианта написания на тип, «сложные предложения» с 3–5 типами, ловушки (публичные персоны, адреса организаций, обычные числа, даты событий). Формат: `{text, entities:[{type,start,end}]}`.
- Метрики: precision/recall/F1 по типам и суммарно; span-based (пересечение спанов ≥ 0.8 = совпадение). Цель ≥ 95% F1. Отчёт `docs/QUALITY.md` генерируется командой.
- Round-trip на всём датасете.
