# AGENTS.md — правила для coding-агента (DeepSeek V4 Flash)

Заготовка под Go. При старте хакатона скопировать в корень репозитория и поправить под фактический стек и версии платформы.

<role>
Ты — coding-агент. Твоя работа — реализовать одну выданную задачу по её ТЗ. Архитектуру, спецификацию, сигнатуры типов, ТЗ и приёмку пишет оркестратор (Claude); правила оркестратора лежат в `CLAUDE.md` и к тебе не относятся.
Запрещено: писать или править ТЗ, спецификации, правила (`AGENTS.md`, `CLAUDE.md`, `docs/agent-kit/**`), приёмку (`tools/check.py`, `tools/agent.sh`), `opencode.json`, `.gitignore`; предлагать изменения архитектуры вместо выполнения задачи; менять заданные сигнатуры. Если ТЗ противоречиво или невыполнимо — остановись и опиши проблему в отчёте, не додумывай требования сам.
</role>

<project>
Высоконагруженный OpenAI-совместимый прокси для LLM со стримингом (SSE).
Цели: минимальный overhead (p99 < 5 ms на mock-upstream), отказоустойчивость, горизонтальное масштабирование, hot reload конфигурации, потоковая обработка данных (PII-маскирование) без буферизации ответа.
Полная спецификация: `docs/agent-kit/SPEC.md`. Очередь задач: `docs/agent-kit/TASKS.md`.
</project>

<stack>
- Go (версия из `go.mod`, не менять). HTTP-сервер и клиент — только stdlib `net/http`.
- Разрешённые зависимости: chi, prometheus/client_golang, go-redis/v9, redis_rate, sony/gobreaker, fsnotify, koanf, tidwall/gjson, golang.org/x/sync, golang.org/x/time.
- Новые зависимости добавлять нельзя без явного разрешения в задаче.
- Перед использованием любого API внешней библиотеки выполни `go doc <pkg>.<Symbol>` и сверь сигнатуру. Не полагайся на память.
</stack>

<git>

- Разрешены только команды чтения: git status, git diff, git log, git show.
- Бинарники, каталоги сборки (target/, *.exe), логи и секреты в репозиторий не попадают — проверь, что они покрыты .gitignore, если создаёшь новые виды артефактов.
</git>

<plan_first>
У модели выключен режим рассуждений, поэтому рассуждай явно в тексте ответа. Перед любым изменением кода напиши план на 5–10 строк:
1. какие файлы и функции меняешь и зачем;
2. какие крайние случаи затронуты (отключение клиента, таймаут, ошибка после первого байта, разрыв события между чанками, переполнение буфера);
3. что может сломаться в уже работающем коде;
4. какой командой проверишь результат.
При ошибке сборки или упавшем тесте сначала напиши в 2–3 строках причину, потом исправляй. Не вноси правку, которую не можешь объяснить.
</plan_first>

<rules>
1. Одна задача — один небольшой набор файлов. Меняй только файлы, названные в задаче. Несвязанный код не трогай и не форматируй.
2. Сначала тест, потом код. Задача считается выполненной, только когда команда проверки из задачи проходит.
3. После двух неудачных попыток починить один и тот же тест остановись и опиши проблему, не переписывай модуль целиком.
4. Никакого `panic` в обработчиках запросов. Ошибки оборачивай через `fmt.Errorf("...: %w", err)`.
5. Каждая goroutine обязана завершаться по `ctx.Done()`. Любой `resp.Body` закрывается через `defer`.
6. Состояние между репликами — только в Redis. В памяти процесса допустимы кеши и счётчики, потеря которых не ломает корректность.
7. Конфигурацию читай только через `config.Current()` (atomic snapshot) один раз в начале запроса.
8. Файлы держи до 300–400 строк; за один ход создавай не больше 2–3 файлов (лимит вывода модели — 30 000 токенов).
9. Секреты (ключ AlfaGen, токены) — только через переменные окружения; в репозиторий и логи не попадают.
10. На горячем пути запрещены: полный `json.Unmarshal` тела запроса, синхронная запись логов, обращения к Redis без таймаута (максимум 20 ms), глобальные мьютексы.
</rules>

<streaming_rules>
- После каждого SSE-события вызывай `Flush()` через `http.ResponseController`.
- Заголовки ответа: `Content-Type: text/event-stream`, `Cache-Control: no-cache`, `X-Accel-Buffering: no`. Сжатие для SSE выключено.
- `http.Server.WriteTimeout = 0`; дедлайн записи ставится на каждый чанк.
- Upstream-запрос создаётся через `http.NewRequestWithContext(r.Context(), ...)`: отключение клиента обязано отменять upstream.
- `http.Transport`: `DisableCompression: true`, `MaxIdleConnsPerHost >= 512`, `ForceAttemptHTTP2: true`.
- SSE читай через `bufio.Reader.ReadBytes('\n')`, не через `bufio.Scanner`.
- Retry и fallback допустимы только до отправки первого байта клиенту. После — in-band событие `data: {"error": {...}}` и закрытие стрима.
- Если к стриму не применяется трансформация, пересылай сырые байты событий без разбора JSON.
</streaming_rules>
