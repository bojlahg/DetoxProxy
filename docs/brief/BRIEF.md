# Брифинг 22.09.2026 — условия задачи (дословно со слайдов)

## Проблематика
- Рост запросов к LLM → рост рисков утечки ПД.
- Соответствие требованиям законодательства РФ и ЦБ.
- Переход от разрозненных решений к единому стандарту безопасности.
- Критерии: качество, отказоустойчивость, масштабируемость.

## Образ решения
- Решение должно легко встраиваться в цепочку взаимодействия «система-потребитель — LLM».
- Обязательное покрытие описанных типов персональных данных.
- Выполнение SLA на ответы и действия (скорость, доступность, стабильность).
- Недопустимость критичных ошибок и соблюдение уровня качества обработки.
- Строгое соблюдение требований безопасности и приватности: никаких утечек, шифрование, минимизация данных.

## Основные требования
1. **Функционал:** Идентификация → Маскирование → Демаскирование.
2. **Качество:** точность обработки не менее **95%**.
3. **Несколько систем-потребителей** с индивидуальными настройками.
4. **Логирование.**
5. **Обработка контекста:** поддержка массивов до **100 000 токенов**.
6. **Производительность:** Latency ≤ 1 сек, целевой RPS ≥ 1000.

## Дополнительные требования
- Токенизация/детокенизация либо замена синтетическими данными.
- Гибкая настройка вида маскирования/токенизации в зависимости от системы.
- RPS 2000 при Latency не более 1 секунды.
- Идентификация документов, удостоверяющих личность, кроме паспорта РФ.
- **Маскирование только при наличии нескольких однозначно идентифицированных типов ПД** (пример: «пин-код карты» — не маскируем; «пин-код карты + номер карты» — маскируем).
- Возможность изменения этих настроек.

## 7. Автоматическая проверка решений (документ организаторов)
**Обе проверки обязательны.** Решение, не прошедшее автопроверку качества кода, а также не развёрнутое для нагрузочного тестирования, **не будет учтено**.

### 7.1 Автопроверка качества кода
- Загрузка решения — **только zip-файл**; проверка запускается автоматически, без её прохождения решение не учитывается.
- В zip: только исходный код. Без объёмных файлов (датасеты, дампы, архивы, медиа, бинарники). Без build-директорий и зависимостей: node_modules, .venv, venv, env; target, build, dist, out, bin, obj; .git, .idea, __pycache__, coverage.
- Один архив разумного размера, исходники в корне или в понятной структуре.

### 7.2 Нагрузочное тестирование
- **Обязательно развернуть решение**, реализующее контракт API: эндпоинт **`POST /process`**.
- Проверяющая система подаёт нагрузку по **эталонному датасету** и оценивает **точность маскирования и демаскирования**, а также **поведение под нагрузкой**.
- Контракт API — Приложение A; инструкция по прохождению проверки — Приложение B. Решение должно быть доступно по указанному URL на момент прогона.

### Следствия
- Нужен **публично доступный URL** — значит, деплой на сервер с внешним IP/доменом (или туннель). Это отдельная задача с дедлайном до 23.09 23:59; страховка — второй экземпляр.
- Точность меряет машина по своему датасету, а не мы — 95% нужно достигать на *их* данных. Наш датасет — только прокси-оценка.
- «Поведение под нагрузкой» — RPS 1000–2000, latency ≤ 1 с на `/process`. Значит, детекция должна быть быстрой; Python-sidecar на каждый запрос при 2000 RPS — риск.
- Zip делать скриптом из `git archive` по .gitignore, проверять содержимое перед отправкой.

## Оценка финалистов (3 этап, топ-менеджмент; шкала 1/2/3 по четырём вопросам)
Формат: команда прогоняет **текст жюри** прямо на встрече, показывает маскирование и восстановление.

**Стоп-сигнал:** реальные ПДн ушли в LLM без маскирования на живом демо — не «минус балл», а провал ключевой функции; утечка перевешивает любые технические достоинства.

### 1. Доверие
Хорошо: ни один фрагмент ПДн не ушёл в LLM открыто; замаскированный текст корректно возвращается в исходный вид, ничего не «потерялось»; **не паникует на ловушках: поэт Александр Пушкин и адрес офиса — не данные клиента.**
Плохо: хоть одна утечка; демаскирование «примерно» или не работает; маскирует всё подряд и ломает смысл запроса к LLM.

### 2. Внедряемость
Хорошо: скорость показана цифрами и метриками, а не обещаниями; маскирование включается/выключается/настраивается под каждую систему-потребитель без правки кода; новые типы данных добавляются через настройку или справочник, а не правкой ядра.
Плохо: «производительность и настройки — потом»; логика зашита под один сценарий демо; нет управления поведением по потребителям.

### 3. Сила решения
Хорошо: осмысленные возможности сверх базы — токенизация или синтетика, маскирование по комбинации данных, документы кроме паспорта РФ, повышенная нагрузка; команда понимает, где её подход даёт сбой, и говорит об этом честно; каждая фича имеет бизнес-причину.
Плохо: фичи «для галочки»; не связано с пользой для бизнеса; впечатляет только на словах.

### Следствия для продукта
- Ловушки: **публичные персоны, адреса организаций, исторические даты** — не ПДн. Нужен механизм исключений: allow-list (известные публичные имена, адреса офисов), контекстные признаки («поэт», «офис», «ул. Ленина, д. 1, офис компании»). Это прямо в чек-листе жюри — обязательная фича, не «доп. сценарий».
- Демаскирование должно быть **побайтово точным** — «ничего не потерялось». Round-trip тест: unmask(mask(x)) == x на всём датасете.
- Не маскировать всё подряд: precision важна не меньше recall. Правило «≥2 типов» из постановки — про это.
- Типы ПДн и правила — **в справочнике/конфиге**, добавление нового типа без правки ядра: демо «добавили тип СНИЛС в YAML → работает» стоит показать живьём.
- На защите жюри даёт свой текст: нужен интерактивный UI или очень простая curl-инструкция с мгновенным ответом.

## Онбординг (полный ТЗ трека, `docs/brief/onboarding.pdf`, `zadacha.txt`)

### Приложение A — контракт `POST /process` (обязателен, по нему идёт автопрогон)
```
POST /process   Content-Type: application/json
{ "payload": "<строка>", "payload_id": "<идентификатор>" }  →  200 { "result": "<строка>" }
```
- Один эндпоинт на маскирование и демаскирование. Направление — по `payload_id`: первый запрос с новым id = маскирование (вернуть маску, запомнить соответствие); второй с тем же id = демаскирование (payload = наша маска → вернуть исходную строку).
- Ответ всегда `{"result": "…"}`. 429 допустим под нагрузкой (система ждёт `Retry-After` и ретраит); 4XX/5XX — ошибки.
- HTTP или HTTPS (self-signed допустим, ssl_verify=false).
- Пример из контракта: `"Клиент Иванов Иван Иванович, паспорт 4509 123456"` → `"Клиент И. И. И., паспорт 45** ****56"`.

### Приложение B — нагрузочная проверка
- Метрика маскирования: **нормированное span-based расстояние Левенштейна [0..1] до эталонной маски**. Метрика демаскирования: сравнение с исходной строкой датасета.
- Категории: ФИО, даты, паспорт, гражданство, орган выдачи, код подразделения, в/у, адрес, email, телефон, ИНН, номер карты, CVV, ПИН, имя держателя **и сложные предложения**.
- Таймаут запроса **10 с** (дольше = неответ). До 2 ретраев (3 попытки) — **эндпоинт должен быть идемпотентным по `payload_id`**: повторный запрос маскирования с тем же id и тем же payload возвращает ту же маску; повторное демаскирование — ту же исходную.
- Стоп прогона после **5 невалидных ответов подряд** (429 не считается, успех сбрасывает счётчик).
- Нагрузка: ~5 минут, все категории, целевой RPS 1000, элементы переиспользуются; latency ≤ 1 с — ориентир, не жёсткий лимит.
- Эталонный сервис `https://process-test.holydev.space/process` — **проверено 22.09: возвращает payload без изменений**, формат маски по нему выяснить нельзя.

### Что известно о формате маски (критично: Левенштейн до эталона)
- Единственный пример: ФИО → инициалы с точками `И. И. И.`; паспорт → первые 2 и последние 2 цифры видны, остальное `*` с сохранением пробела: `45** ****56`. Слайд: `Иванов Иван Иванович 4503 1237846` → `*.*.* 4*** *****6` (другой вариант!). Два примера противоречат друг другу в деталях → формат для остальных 15 типов неизвестен.
- **Вопрос №1 в поддержку: есть ли спецификация формата эталонной маски по типам или пример датасета?** Без этого 6+4 балла и «95%» — лотерея.
- Стратегия при отсутствии ответа: маска сохраняет длину и структуру (пробелы, дефисы, точки), заменяя символы на `*`, с открытыми первыми/последними символами по типу как в примере паспорта. Левенштейн штрафует за длину, поэтому «сохранить длину» — безопаснее плейсхолдеров вроде `<CARD_1>`.

## Ответы организаторов из эфира (стенограмма `briefing-transcript.md`, Q&A 00:42–00:53)
- **Эталонной маски нет.** «Маски вы можете использовать самостоятельно, какие считаете нужным. В описании обязательно приложить, какие вы используете маски, чтобы мы могли это проверить.» → формат маски свободный; **документ с описанием масок по каждому типу — обязательный артефакт**.
- **Оценка span-based**: сравниваются не строки целиком, а только значащие части (спаны). Демаскирование — по степени похожести, той же логикой; на демаскирование подаётся наша же маска.
- **payload_id всегда уникален**, даже при повторе текста по второму кругу.
- **Язык текстов — русский**; английский — задача со звёздочкой.
- **Инфраструктура для НТ — своя.** Мощностей не дают; принимают почти любой URL, вплоть до туннеля к локальной машине на период проверки (тогда написать организаторам). Ресурсы сервера — на наше усмотрение, лишь бы могли обосновать. Рекомендуют российские серверы, страна формально не влияет.
- **Ресурсы жюри при локальной проверке**: 4–6 ядер, 8 ГБ RAM, без GPU — решение должно запускаться на таком ноутбуке.
- **UI не нужен**: «модуль работает под капотом, важнее решение, не картинка». UI — только если хотим для питчинга.
- **Промежуточная автопроверка**: предварительно да, можно загружать zip заранее; подтвердят в чате.
- **Языки**: Python, Java, Go — «удобнее, проще, быстрее»; «в целом можем проверять на других языках».
