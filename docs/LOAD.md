# Нагрузка и задержки

## Стенд

- Сервер: VPS 4 ядра, 8 ГБ, Ubuntu 26.04, один процесс `detox-proxy` (systemd, порт 8080).
- Генератор: `tools/loadgen` (Go), **на том же сервере** — он отнимает часть тех же 4 ядер, поэтому все цифры ниже занижены относительно чистого стенда.
- Схема повторяет автопроверку: замкнутый цикл, 200 одновременных соединений, на каждое маскирование сразу демаскирование того же текста с тем же `payload_id`.
- Тексты: 3000 реальных строк из HiveTrace, rmr-бенчмарка и нашей синтетики; медиана 127 байт, p95 556 байт.
- Ревизия `558bd42`, 22.09.2026 23:11.

## Результаты

| Нагрузка | Маскирование p50 / p95 / p99 | Демаскирование p50 / p95 / p99 | Ошибки | Round-trip |
|---|---|---|---|---|
| 1000 масок/с (+1000 демасок/с) | 0,95 / 3,2 / 6,2 мс | 0,40 / 1,3 / 2,4 мс | 0 | 100% |
| 2000 масок/с (+2000 демасок/с) | 1,09 / 3,5 / 6,6 мс | 0,52 / 1,8 / 3,1 мс | 0 | 100% |
| Предел (без ограничения темпа) | 30 / 60 / 76 мс при **~3200 масок/с + 3200 демасок/с** | 29 / 59 / 75 мс | 0 | 100% |

- Требование задания — до 1 с на запрос; цель жюри — 0,5 с. На целевых 1000 RPS запас более чем стократный.
- Бонусная планка 2000 RPS держится с теми же задержками: сервис ещё далёк от насыщения.
- Предел по пропускной способности — около **6400 запросов/с** суммарно, без единой ошибки и без единого расхождения при восстановлении (320 720 запросов в прогоне).
- Память: 284 МБ при 203 тыс. сохранённых соответствий (≈1,1 КБ на запись).

## Реальная нагрузка автопроверки (для сравнения)

Журнал сервиса за 22.09: два прогона организаторов, каждый ~5–6 минут, около **350 запросов/с**, по 105–113 тыс. запросов за прогон. Все ответы 200, ни одного 429, 5xx или перезапуска.

## Что мы нашли нагрузкой и починили

1. **Обвал на переполнении хранилища.** При достижении `mapping_max_entries` каждая вставка делала полный обход таблицы дважды (уборка просроченных + поиск самой старой записи). На 200 тыс. записей пропускная способность падала с 6400 до 700 запросов/с, задержка росла до 1 с. Исправлено в T25: порядок вставки хранится очередью, вытеснение за O(1), уборка по TTL — фоновой задачей раз в 5 секунд в отдельном пуле потоков; лимит поднят до 2 млн записей (≈2,3 ГБ на пределе).
2. **Детекция блокировала рабочие потоки.** Тяжёлые тексты обрабатывались прямо в async-задаче, из-за чего дедлайн запроса не срабатывал, а короткие запросы ждали. Исправлено в T17: тексты больше `inline_max_bytes` уходят в пул блокирующих потоков под семафором, при исчерпании дедлайна возвращается 503 с `Retry-After`.
3. **Падение процесса на неразрывном пробеле.** Один текст с U+202F ронял весь сервис. Исправлено в HF1 и T19, добавлен постоянный тест (`tests/unicode_safety.rs`); в release-профиле `panic = "unwind"`, поэтому паника в одном запросе больше не убивает процесс.

## Известное ограничение

На искусственно плотном тексте (9 КБ, 400 ИНН подряд) обработка занимает ~150 мс: часть проверок контекста выполняется для каждой пары найденных сущностей. На реальных текстах, где сущностей единицы, это не проявляется (p99 6,6 мс под нагрузкой 2000 RPS). Оптимизация — задача T09.

## Как повторить

```bash
cd tools/loadgen && GOOS=linux GOARCH=amd64 go build -o loadgen .
# texts.jsonl — любой файл формата tests/data/*.jsonl (нужно поле "text")
./loadgen -url http://127.0.0.1:8080 -texts texts.jsonl -c 200 -d 60s -ramp 10s          # предел
./loadgen -url http://127.0.0.1:8080 -texts texts.jsonl -c 200 -d 30s -ramp 5s -rps 1000 # целевой темп
```
