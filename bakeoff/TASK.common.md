<task>
  <goal>
    Написать небольшой HTTP-прокси для LLM API (OpenAI-совместимый, со стримингом SSE).
    Задача считается выполненной только тогда, когда команда проверки завершается с кодом 0 и строкой «ИТОГ: 10/10».
  </goal>

  <contract>
    Конфигурация — только через переменные окружения:
    - LISTEN_ADDR — адрес прослушивания, например 127.0.0.1:18080
    - UPSTREAMS — список upstream через запятую в порядке приоритета, например http://127.0.0.1:18081,http://127.0.0.1:18082 (только plain HTTP/1.1, без TLS)
    - TTFT_TIMEOUT_MS — сколько ждать ПЕРВОЕ SSE-событие от upstream (по умолчанию 5000)

    Эндпоинты:
    - GET /healthz → 200
    - GET /metrics → 200, текст в формате Prometheus, обязателен счётчик proxy_requests_total (число принятых POST-запросов)
    - POST /v1/chat/completions → проксируется на upstream по тому же пути
  </contract>

  <requirements>
    1. Тело запроса и заголовок Authorization передаются upstream без изменений. Ответ upstream передаётся клиенту без изменений.
    2. Если в теле "stream": true — ответ приходит как text/event-stream. Каждое событие пересылается клиенту немедленно (без буферизации, с flush); добавленная задержка на событие — единицы миллисекунд.
    3. Если клиент закрыл соединение посреди стрима, прокси обязан немедленно закрыть соединение с upstream (иначе upstream продолжает генерацию впустую).
    4. Failover ДО первого байта клиенту: если upstream ответил 5xx или 429, не удалось подключиться, или первое SSE-событие не пришло за TTFT_TIMEOUT_MS — запрос повторяется на следующем upstream из списка. Важно: upstream может сразу прислать «200 OK» и заголовки, а первое событие задержать — таймаут считается до первого события тела, а не до заголовков. Зависшая попытка обязана быть отменена (соединение закрыто).
    5. Если все upstream отказали — ответ 502 или 503 с JSON-телом {"error": {"message": "...", "type": "..."}}.
    6. ПОСЛЕ отправки первого байта клиенту retry запрещён. Если upstream оборвал стрим посередине — уже полученные события доставлены, клиентский стрим завершается (закрытием соединения или событием data: {"error": ...}), клиент не должен зависнуть.
    7. Прокси держит минимум 200 одновременных стримов без потерь событий и не падает.
  </requirements>

  <rules>
    - Файл check.py изменять запрещено. Он сам поднимает фейковые upstream и запускает прокси.
    - Сначала прочитай check.py, чтобы точно понять, что проверяется.
    - Работай итерациями: собери → запусти проверку → исправь первый упавший тест → повтори. Лог прокси проверка пишет в proxy.log.
    - Не останавливайся и не задавай вопросов, пока проверка не станет зелёной. Если после 3 попыток один и тот же тест не проходит — перечитай check.py и требования, а не переписывай всё заново.
    - В конце создай файл REPORT.md: что сделано, сколько итераций проверки понадобилось, какие были проблемы.
  </rules>
