# Сравнение стеков на тестовой задаче (21.09.2026)

Одно и то же ТЗ (`TASK.common.md` + раздел про стек) выдано DeepSeek-V4-Flash-0731 через OpenCode 1.18.31 (`opencode run --auto`, провайдер `alfagen`) в трёх папках. Приёмка — общая чёрный ящик-проверка `check.py` (10 тестов: passthrough, стрим без буферизации, отмена upstream при отключении клиента, failover до первого байта, все upstream недоступны, TTFT-таймаут при уже пришедших заголовках, обрыв посреди стрима без retry, метрики, 200 одновременных стримов, отсутствие падений).

Условия: **thinking у модели был выключен** (0 reasoning-токенов во всех сессиях). Go и Rust собирались и проверялись нативно на Windows, C — в WSL (Linux, epoll), поэтому задержки C с остальными напрямую не сравнимы.

## Ревью кода (что проверка не ловит)

**Go** — работает, но с типичными ошибками модели без обдумывания:
- на каждый запрос создаётся новый `http.Transport` с `DisableKeepAlives: true`: нет пула соединений, под нагрузкой это TCP-handshake на каждый запрос и исчерпание портов;
- в `streamRest` goroutine продолжает писать в `ResponseWriter` после выхода из обработчика по `ctx.Done()` — гонка данных и возможная паника;
- нет таймаута на connect и на non-stream ответ; тело читается без лимита и целиком разбирается `json.Unmarshal`.

**Rust** — структурно лучший из трёх:
- общий `reqwest::Client` с пулом в `AppState`;
- отмена upstream и отмена зависшей попытки корректны по построению: стрим принадлежит телу ответа, при сбросе соединение закрывается; гонок нет;
- замечания: `to_bytes(body, usize::MAX)` без лимита, разбор всего тела в `serde_json::Value`, нет connect-таймаута, не выставлен `TCP_NODELAY` на серверном сокете.

**C** — аккуратнее ожидаемого (границы буферов проверяются, ASan чист), но:
- блокирующий `gethostbyname` внутри event loop — DNS-задержка останавливает все стримы;
- один поток на один epoll: одно ядро, для масштабирования нужен запуск процесса на ядро с `SO_REUSEPORT`;
- `realloc` без проверки результата, линейный обход таблицы соединений на каждый тик таймеров;
- и это без TLS, HTTP/2, пула соединений, Redis и JSON — всего, что в Go и Rust даёт готовая библиотека, а в C пришлось бы писать или прикручивать.

## Выводы

1. **C отпадает по цене, а не по возможности.** Модель справилась, но в 4–8 раз дольше и в 5–10 раз дороже по токенам, чем Rust, на задаче без TLS и HTTP/2. На полном объёме хакатона (30+ задач) этот множитель съедает весь запас времени.
2. **Rust реален даже без thinking.** 3 минуты, 181 строка, ошибки сборки исправлены самостоятельно, API axum 0.8 и reqwest 0.13 модель знает. Опасение «агент завязнет в borrow checker» на этой задаче не подтвердилось.
3. **Rust дал более корректный код, чем Go.** Две серьёзные ошибки Go-решения (гонка с `ResponseWriter`, отсутствие пула) в Rust-решении отсутствуют: первую не пропустил бы компилятор, вторую модель не сделала, потому что `Client` естественно ложится в общее состояние. Для кода, который пишет ИИ и некогда вычитывать, это весомый довод.
4. Go быстрее примерно вдвое по времени агента; на 30+ задачах это часы. Решение по стеку: Rust с контрольной точкой остаётся в силе, запасной вариант — Go.
5. Проверка-приёмка работает как метод: все три агента дошли до зелёного результата без вмешательства человека. На хакатоне каждую задачу выдавать с исполняемой приёмкой.
6. Ревью сильной моделью обязательно: приёмка зелёная, а ошибки под нагрузкой остаются.
