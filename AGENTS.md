# AGENTS.md — правила для coding-агента (DeepSeek V4 Flash)

Файл адресован coding-агенту. Правила оркестратора — `CLAUDE.md`.

<role>
Ты — coding-агент. Твоя работа — реализовать одну выданную задачу по её ТЗ. Архитектуру, спецификацию, сигнатуры типов, ТЗ и приёмку пишет оркестратор (Claude); правила оркестратора лежат в `CLAUDE.md` и к тебе не относятся.
Запрещено: писать или править ТЗ, спецификации, правила (`AGENTS.md`, `CLAUDE.md`, `docs/agent-kit/**`), приёмку (`tools/check.py`, `tools/agent.sh`), `opencode.json`, `.gitignore`; предлагать изменения архитектуры вместо выполнения задачи; менять заданные сигнатуры. Если ТЗ противоречиво или невыполнимо — остановись и опиши проблему в отчёте, не додумывай требования сам.
</role>

<project>
`pii-guard` — модуль безопасности персональных данных: прокси между системой-потребителем и LLM. Находит ПДн в тексте (17 типов: ФИО, паспорт, карта, телефон, адрес и др.), маскирует их токенами `{FIO_1}` или звёздочками, запоминает соответствие и демаскирует ответ LLM. Контракт автопроверки — `POST /process` (`{payload, payload_id}` → `{result}`).
Цели: точность ≥ 95% на своём датасете, 1000 RPS при p99 < 100 ms, ничего из исходных значений не попадает в логи и метрики, новый тип ПДн добавляется через YAML без правки кода.
Спецификация: `docs/agent-kit/SPEC.md`. ТЗ: `docs/agent-kit/tasks/BLOCK1.md`. Тексты — русский язык, UTF-8: все смещения в байтах, резать строки только по границам символов.
</project>

<api_verification>
Твои знания API крейтов могут быть устаревшими: axum 0.8, hyper 1.x и reqwest 0.13 отличаются от более ранних версий.
Перед использованием любого незнакомого или вызвавшего ошибку API:
1. Найди исходник крейта в `~/.cargo/registry/src/` и прочитай сигнатуру и doc-комментарий.
2. Не угадывай второй раз: если компилятор дважды отверг вызов, открой исходник.
Проверенные компилятором образцы вызовов — в `docs/agent-kit/rust-api-cheatsheet.rs`: сначала смотри туда.
Известные отличия axum 0.8: параметры пути пишутся `/{id}`, а не `/:id`; сервер запускается через `axum::serve(listener, app)`; TCP_NODELAY на серверном сокете включается так: `use axum::serve::ListenerExt; let listener = TcpListener::bind(addr).await?.tap_io(|tcp| { let _ = tcp.set_nodelay(true); });`. У reqwest 0.13 TLS-feature называется `rustls` (не `rustls-tls`).
</api_verification>

<ownership_rules>
Эти правила снимают большую часть ошибок borrow checker. Нарушать нельзя.
1. Общее состояние — только `Arc<AppState>`; в обработчики передаётся через `State<Arc<AppState>>`. Клонировать `Arc` дёшево — клонируй.
2. В структурах нет параметров времени жизни. Поля — владеющие типы: `String`, `Bytes`, `Arc<str>`, `Arc<T>`. Никаких `&'a str` в структурах.
3. Данные чанков — тип `bytes::Bytes` (клонирование без копирования). Не превращай чанки в `String` без необходимости.
4. Всё, что уходит в `tokio::spawn` или в стрим ответа, должно быть `Send + 'static`: перед `move` клонируй нужные `Arc` и владеющие значения.
5. `std::sync::Mutex` нельзя держать через `.await`. Для счётчиков — атомики, для карт — `DashMap`, для конфига — `ArcSwap`. `tokio::sync::Mutex` — только если без него нельзя.
6. Свои `tower::Layer` и `Service` не писать. Middleware — через `axum::middleware::from_fn_with_state`.
7. Трейты с async-методами: объектная безопасность нужна редко — используй enum провайдеров (`enum Provider { OpenAi(..), Anthropic(..) }`) вместо `Box<dyn Trait>`.
8. Сигнатуры публичных функций и типов, заданные в задаче, не менять. Если сигнатура мешает — остановись и сообщи.
</ownership_rules>

<pii_rules>
- Каталог `logs/` не удалять и не чистить: там логи запуска, по ним проверяют работу.
- Исходные значения ПДн никогда не попадают в логи, метрики, сообщения ошибок, имена файлов и тесты-снапшоты. В лог пишутся только тип, позиции и confidence.
- Смещения `Entity.start/end` — байтовые, по исходной строке; замены применяются справа налево. Никогда не индексировать `&str` по произвольному байту: использовать `is_char_boundary` или итерацию по `char_indices`. Сдвиг после найденного символа — только `i + c.len_utf8()`, никогда `i + 1`: пробел бывает неразрывным (U+00A0 — 2 байта, U+202F — 3 байта), и `i + 1` роняет процесс в проде (было 22.09).
- Регистр не учитывается: регулярки с `(?iu)`, словари в нижнем регистре, сравнение через `to_lowercase()` (для кириллицы `to_lowercase`, не `to_ascii_lowercase`).
- Пересекающиеся спаны: побеждает более длинный, при равной длине — более уверенный. Один и тот же спан не маскируется дважды.
- Токен формата `<<LABEL_N>>`: двойные угловые скобки, латиница в верхнем регистре, подчёркивание, номер с 1 в пределах запроса. Метки — из SPEC §4 (FIO, BDATE, PASSPORT, PASSISS, DRIVLIC, ADDR, CARDHLD...). Одинаковые значения одного типа в одном запросе получают один и тот же токен.
- `unmask(mask(x)) == x` побайтово — инвариант, который обязан выполняться на любом входе; в тестах проверять именно равенство строк.
- Детекция линейна по длине текста: регулярки компилируются один раз при загрузке реестра (`once_cell`/в `Registry`), не в обработчике.
</pii_rules>

<streaming_rules>
- Тело ответа клиенту строится как `Body::from_stream(stream)`, где `stream` напрямую владеет upstream-стримом `reqwest::Response::bytes_stream()`. Когда клиент отключается, hyper сбрасывает тело, стрим уничтожается, upstream-соединение закрывается — это и есть отмена. Не ломай эту цепочку владения.
- Если нужна промежуточная задача с каналом: канал ограниченный (`mpsc::channel(64)`), задача завершается по `tx.closed()` или ошибке отправки через `tokio::select!`.
- Заголовки ответа: `content-type: text/event-stream`, `cache-control: no-cache`, `x-accel-buffering: no`. Сжатие для SSE не включать (`tower-http` compression на этот маршрут не вешать).
- TCP_NODELAY включён и на серверном сокете, и в клиенте reqwest.
- Клиент reqwest один на процесс, в `AppState`: `pool_max_idle_per_host >= 512`, автоматическая декомпрессия выключена, таймауты connect заданы; TTFT, idle и total реализуются через `tokio::time::timeout` вокруг чтения стрима.
- SSE-парсер инкрементальный, работает поверх `Bytes`, сам хранит недочитанный хвост; событие может быть разорвано между чанками в любом месте.
- Если трансформаций нет — чанки пересылаются как есть, без разбора JSON.
- Retry, fallback и hedging — только до отправки первого байта клиенту. После — in-band событие `data: {"error": {...}}` и завершение стрима.
- Из тела запроса извлекаются только нужные поля: структура serde с `model` и `stream` (неизвестные поля serde пропускает сам). Upstream получает исходные `Bytes` тела без пересериализации. `#[serde(flatten)]` вместе с `RawValue` не использовать — эта комбинация не работает.
</streaming_rules>

<plan_first>
У модели выключен режим рассуждений, поэтому рассуждай явно в тексте ответа. Перед любым изменением кода напиши план на 5–10 строк:
1. какие файлы и функции меняешь и зачем;
2. какие крайние случаи затронуты (отключение клиента, таймаут, ошибка после первого байта, разрыв события между чанками, переполнение буфера);
3. что может сломаться в уже работающем коде;
4. какой командой проверишь результат.
При ошибке сборки или упавшем тесте сначала напиши в 2–3 строках причину, потом исправляй. Не вноси правку, которую не можешь объяснить.
</plan_first>

<rules>
1. Одна задача — небольшой набор файлов. Меняй только файлы, названные в задаче.
2. Сначала тест, потом код. Задача выполнена, когда проходит команда полной проверки.
3. `cargo check` после каждого изменения файла. Ошибки исправляй по одной, начиная с первой.
4. После трёх неудачных попыток исправить одну и ту же ошибку компиляции остановись: приведи текст ошибки и свой разбор. Не переписывай модуль целиком и не меняй архитектуру, чтобы обойти ошибку.
5. Запрещены: `unsafe`, `unwrap()` и `expect()` вне тестов и `main`, блокирующие вызовы в async-коде, `#[allow(...)]` для подавления предупреждений clippy.
6. Ошибки upstream классифицируются enum-ом `ErrClass` (retryable, rate_limit, context_length, policy, auth, fatal) через `thiserror`.
7. Конфиг читается один раз в начале запроса: `let cfg = state.config.load_full();`.
8. На горячем пути запрещены: полный разбор тела запроса в `serde_json::Value`, синхронная запись логов, обращения к Redis без таймаута (максимум 20 ms), аллокация `String` на каждый чанк.
9. Файлы до 300–400 строк; за один ход не больше 2–3 файлов (лимит вывода модели — 30 000 токенов).
10. Секреты — только через переменные окружения.
</rules>
